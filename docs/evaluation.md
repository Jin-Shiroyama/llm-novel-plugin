# 執筆品質の評価手順（「書かせて読む」ベンチマーク）

`llm-novel-plugin` のスキル・プロンプト・ツールを変更した際、単体テスト（整形・照合の正しさ）だけでは「実際に書かれた小説が面白いか」「平坦化やトーン逸脱が起きていないか」を測れません。
この手順書では、`examples/` の見本作品を使って変更前後を同じ条件で比較する進め方を定めます。

---

## 1. 見本作品（`examples/`）

| ディレクトリ | ジャンル・構成 | トーン・設定 | 主な確認ポイント |
|---|---|---|---|
| `examples/romcom-light/` | ラブコメ（`episodic`） | `light` / `worldBuilding: "minimal"` / `indent: "none"` | 軽快な掛け合い、照れ隠しによる一拍の溜め→ニヤニヤの見返り、重い過去・教訓まとめの非混入、字下げなし規約 |
| `examples/fantasy-balanced/` | 異世界ファンタジー（`arc`） | `balanced` / `worldBuilding: "standard"` / `indent: "fullwidth"` | 能力の制約と工夫による溜め→スカッと見返り、ごほうび場面の厚み、用語集・伏線・世界観ルールの整合、全角1字下げ規約 |

いずれも企画書・登場人物（呼称・ことばづかい完備）・プロット概要・第1〜4話の話別プロットが記入済みで、すぐに第1話から執筆を始められる状態（`writing` 段階）です。

---

## 2. 変更前・変更後プラグインの用意

`dist/index.js` は 1 つ上のディレクトリを基準に `commands/` と `skills/` を読み込むため、**変更前のプラグインは `dist/` だけでなくリポジトリ一式で取り出してビルド**します（`git worktree add` が手軽です）。

基準となる変更前コミット（`<比較元コミット>`：例 `HEAD~1` や比較したい基準タグ・ハッシュ）を worktree で取り出してビルドします。

```bash
# 変更前のプラグインを一式取り出してビルドする
git worktree add /tmp/llm-novel-plugin-before <比較元コミット>
cd /tmp/llm-novel-plugin-before
pnpm install && pnpm build   # pnpm が無い環境では npm ci && npm run build

# 変更後のプラグインも最新状態でビルドする
cd /path/to/llm-novel-plugin
pnpm build
```

> **重要**：`opencode.json` の `"plugin"` 配列には**変更前と変更後のどちらか一方だけ**を指定してください。新旧を同時に読み込むとツール名が衝突します。

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["file:///tmp/llm-novel-plugin-before/dist/index.js"]
}
```

変更後を測るときは `plugin` のパスを最新作業ツリーの `dist/index.js` へ切り替えて OpenCode を再起動します。
評価終了後、一時 worktree は `git worktree remove /tmp/llm-novel-plugin-before` で片づけられます。

## 3. 比較実験の設計と費用の目安

### 企画書の「摩擦・ままならなさ」欄の扱い（2 通りの比較）

`examples/` の `concept.md` には最新仕様どおり `- **物語を動かす摩擦・ままならなさ**：...` が入っています。この欄は `## トーンと NG ライン` に含まれるため、変更前のプラグインでもそのまま毎話注入されます。目的に応じて次の 2 通りを使い分けてください。

1. **スキル・プロンプト改善単体の比較**：変更前・変更後とも、コピー先の `.novel/concept.md` から `- **物語を動かす摩擦・ままならなさ**：...` の 1 行を外した同一入力で比較する。
2. **Phase 2 全体（企画書テンプレート＋スキル改善）の比較**：変更前側は摩擦欄を外した版（旧テンプレート相当）、変更後側は `examples/` のまま（摩擦欄あり）でエンドツーエンド比較する。

### 試行回数とブラインド比較

LLM の出力は 1 回ごとのばらつきが大きいため、各条件（変更前／変更後）で **2〜3 回ずつ**別コピーに書かせ、ファイル名やフォルダ名で新旧が分からない形へ伏せたうえで並べて読み比べると判断がぶれません。

### 費用の目安

- フルセット（見本 2 本 × 前後 2 条件 × 2〜3 回 × 3 話）で **24〜36 話分の執筆**（＋採点用レビュー）になります。
- コストと時間を抑えたい場合は、**まず見本 1 本 × 前後 2 条件 × 各 2 回 × 3 話（計 12 話）** から回し、傾向が見えてからもう 1 本へ広げるのが現実的です。

## 4. 評価の実行手順

> **重要**：`examples/` 内で直接執筆を実行すると、本文や記録ファイルが生成されてリポジトリ内の見本データが汚れてしまいます。必ず一時作業ディレクトリへコピーしてから実行してください。

### ステップ 1：見本を別ディレクトリへコピーする

```bash
rm -rf /tmp/eval-romcom-before-1 /tmp/eval-romcom-after-1
cp -r examples/romcom-light /tmp/eval-romcom-before-1
cp -r examples/romcom-light /tmp/eval-romcom-after-1
```

（摩擦欄を外す条件のディレクトリでは、コピー先の `.novel/concept.md` から `- **物語を動かす摩擦・ままならなさ**：...` の行を削除します。）

### ステップ 2：同一モデルで第1〜3話を執筆させる

各コピー先ディレクトリで、対象のプラグイン（変更前または変更後）のみを有効にした OpenCode を起動し、次を実行します。

```text
/write-chapters 1-3
```

推敲オプションの効果を測りたい場合は、**変更後のプラグイン側**で別コピー先に以下を実行し、「変更後（通常）」と「変更後＋`--revise`」を読み比べます（`--revise` は変更後のプラグインのみ対応）。

```text
/write-chapters 1-3 --revise
```

### ステップ 3：同じ基準で採点・機械点検する

> **採点基準をそろえる**：変更前プラグインの `/novel-review` は変更前の編集者（「溜め」の観点なし）で動くため、そのまま比べると採点基準がずれます。**採点は両方とも変更後のプラグイン（最新の `novel-editor`）または人間が同一の採点シートで読む形に統一**し、変更前側で実行した `/novel-review` は参考にとどめてください。

各コピー先に対して（変更後プラグインを有効にした状態で）次を実行し、採点材料と機械指標をそろえます。

```text
/novel-review all
/novel-status
```

あわせて `novel_check` の出力（表記 ❌・文章 ⚠️）と、各話の文字数（目安との差）を記録します。

## 5. 採点シート（人間によるブラインド読み比べ）

`novel-editing` skill の 5 軸に加え、軽快な作品で陥りやすい平坦化を見抜くため **「溜めと見返り」** を独立して採点します。各軸 10 点満点で、2〜3 回の試行の平均または傾向を並べます。

| 観点 | 変更前 (/10) | 変更後 (/10) | 主な確認ポイント |
|---|---:|---:|---|
| 1. キャラ立ち・掛け合い | | | 名前を隠しても誰の台詞か分かるか。「🗣️ ことばづかい」の維持 |
| 2. 見どころ・快感 | | | 第1〜3話でフックの約束を果たしているか。ごほうび場面が削られていないか |
| 2b. 溜めと見返り（平坦化チェック） | | | 起きた困りごと・照れ・制約が 1〜2 往復で都合よく即解決したり、全員が物分かりよく丸く収めたりしていないか |
| 3. テンポ・読みやすさ・つなぎ | | | 文体見本の呼吸に近いか。次話展開を先食いせず、話末の引きが次話の入りへ自然につながるか |
| 4. トーン＆NG ライン遵守 | | | 勝手なシリアス化・重い過去の後付け・説教や教訓まとめが無いか |
| 5. つじつま・表記・反 AI | | | 設定・用語集・状態・伏線の整合。AI 定型句や話またぎ仕草の偏り |

### あわせて記録する機械指標

- **表記 ❌（全3話合計）**：0 件が基準
- **文章 ⚠️（全3話合計）**：AI 定型・教訓まとめ・話末定型締めの件数
- **文字数の目安逸脱**：±15% から外れた話の有無と、水増し／削りすぎの有無
- **記録の完全性**：`/novel-status` で `character-state`・`summary`・`foreshadow` の欠けや異常が無いこと

---

## 6. 変更採用の目安

- 機械指標が悪化しておらず（表記 ❌ 0 件、記録欠け 0 件）、「トーン＆NG ライン遵守」を落とさずに「溜めと見返り」「見どころ・快感」「つなぎ」のいずれかが改善していれば採用と判断します。
- 逆に、語調が説教臭くなったり、日常系・ラブコメに不自然なギスギスが混入したりした場合は、スキル・テンプレートの文言を弱めて再検証します。
